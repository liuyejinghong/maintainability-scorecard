# maintainability-scorecard

> 实战工坊 / [Field Lab](https://github.com/liuyejinghong/field-lab) 的一部分：在真实项目里做出来、持续打磨的 AI Agent 工具。

给 Python 项目做一次结构体检。它扫描代码和 Git 历史，找出最长、最复杂的函数，模块之间的循环依赖和改动最频繁的文件，并统计异常处理、兼容代码和测试写法。

同一个仓库可以选多个提交一起扫，结果按提交并排列在一张表里。重构前留一份底，重构后再扫一次，就能看到结构变化。

可以直接用命令行运行，也可以装成 Claude Code skill，让 Claude 帮你写配置、运行和解读结果。

## 扫描结果示例

下面是一个约 12 万行的 Python 项目在重构前的扫描结果（节选）。

### 规模

| 指标 | 结果 |
| --- | ---: |
| 生产代码文件 | 191 个 |
| 生产代码行数（不含空行和注释） | 120,050 行 |

### 函数

| 指标 | 结果 |
| --- | --- |
| 超过 150 行的函数 | 118 个，占全部函数代码的 30.9% |
| 圈复杂度超过 20 的函数 | 348 个 |
| 最长也最复杂的函数 | `RiskSyncBridge.ensure_risk_orders`：2,636 行，圈复杂度 641 |

按圈复杂度分档后，可以看到代码集中在哪一档：

| 圈复杂度 | 函数数 | 占全部函数代码 |
| --- | ---: | ---: |
| 1–4 | 1,829 | 16.4% |
| 5–9 | 747 | 16.1% |
| 10–24 | 577 | 25.5% |
| 25 及以上 | 281 | 42.0% |

只有 281 个函数的复杂度在 25 以上，却占了四成多的代码。函数行数和参数个数也按同样方式分档。

### 文件

| 指标 | 结果 |
| --- | --- |
| 超过 500 行的文件 | 46 个，占全部代码的 81.0% |

### 模块依赖

| 指标 | 结果 |
| --- | --- |
| 最大的循环依赖 | 45 个文件互相依赖；只算模块加载时执行的导入，是 9 个文件 |
| 写在函数内部的导入 | 254 处 |
| 跨文件访问别处的私有名称（`obj._name`） | 465 处 |

### 异常与兼容代码

| 指标 | 结果 |
| --- | --- |
| `except Exception` | 616 处 |
| 标识符和字符串里的 legacy、retired、historical、deprecated 等字样 | 415 处 |
| 带版本号的协议字符串（形如 `name/v1`） | 96 种，共出现 165 次 |

### 测试

| 指标 | 结果 |
| --- | --- |
| 测试文件 / 行数 | 226 个 / 158,499 行 |
| 测试中访问私有名称 | 5,355 处 |
| 测试替身（`MagicMock`、`monkeypatch` 等）引用 | 889 处 |

### 改动热点

扫描提交前 90 天里改动最多的文件，与复杂度放在一起：

| 文件 | 提交次数 | 增删行 | 复杂度合计 | 最长函数 |
| --- | ---: | ---: | ---: | ---: |
| `gateway/strategy_instance.py` | 122 | +7,082 / −1,552 | 3,064 | 1,165 行 |
| `trading_node.py` | 80 | +2,239 / −1,385 | 930 | 567 行 |
| `gateway/risk_guard.py` | 60 | +6,396 / −5,964 | 882 | 537 行 |

改得最频繁、又最复杂的文件，通常最值得先拆。

### 按项目配置的指标

在配置里写上项目自己的约定，还能统计：

- **共享状态**：指定共享对象的名字，统计它被读写多少次、哪些键被多个文件写入。示例项目有 827 处读写，17 个键被 3 个以上的文件写入。
- **外部写接口**：指定封装外部调用的函数，找出绕过封装直接调用的位置。示例项目有 21 处，分布在 10 个文件里。
- **自定义计数**：统计某些函数的调用次数，或某个正则的出现次数。
- **模块归属**：提供一份清单，写明每个文件属于哪个模块、模块之间允许怎样依赖，报告会列出没有归属的文件、清单里失效的路径、每个模块的依赖数，以及违反依赖方向的导入。示例项目有 32 个文件没有归属，75 处导入违反依赖方向。

每次运行输出两份结果：JSON 包含全部数据和每个指标的定义，Markdown 是一页摘要。

## 安装

需要 Python 3.11+ 和 `git`，没有第三方依赖。

作为 Claude Code skill 使用：

```bash
git clone https://github.com/liuyejinghong/maintainability-scorecard.git \
  ~/.claude/skills/maintainability-scorecard
```

然后对 Claude 说：“用 maintainability-scorecard 对比这个仓库 v1.0 和 main 两个版本。”

单独使用时，克隆到任意目录即可。

## 使用

```bash
python3 scripts/scorecard.py \
  --repo /path/to/project \
  --config my-scorecard.toml \
  --snapshot before=v1.0 \
  --snapshot after=main \
  --json out/scorecard.json \
  --markdown out/scorecard.md
```

- `--snapshot 名称=提交` 可以写多次，每个提交在结果表里占一列。
- 只写 `--json` 或 `--markdown` 中的一个也可以；两个都不写时，JSON 输出到终端。
- `--embed page.html` 把结果写进已有 HTML 页面里的 `<script type="application/json" id="scorecard-data">` 块，方便做自己的报告页。

每个提交先用 `git archive` 导出到临时目录再测量，你的工作区和当前分支保持原样。

## 配置

复制 [`examples/scorecard.toml`](examples/scorecard.toml) 再修改。主要部分：

| 配置段 | 内容 |
| --- | --- |
| `[project]` | 项目名、生产代码目录、导入前缀 |
| `[scope]` | 扫描和排除的文件 |
| `[thresholds]` | 长函数、高复杂度、大文件的界线，默认 150 行、20、500 行 |
| `[tests]` | 哪些文件算测试，统计哪些测试替身 |
| `[fallbacks]` | 兼容字样词表、版本号字符串的正则 |
| `[risk_tiers]` | 分档界线 |
| `[hotspots]` | 热点回看天数，要排除的批量格式化提交 |
| `[shared_state]`、`[write_interfaces]`、`[[custom_counters]]`、`[module_index]` | 按项目配置的指标（可选） |
| `[[snapshots]]` | 要扫描的提交，也可以在命令行指定 |

配置里写错键名、类型或正则时，工具会直接报错。

## 指标怎么算

| 指标 | 算法 |
| --- | --- |
| 函数行数 | 函数自身的行数，嵌套在里面的函数和类单独计算 |
| 圈复杂度 | 由语法树近似计算：从 1 开始，每个 `if`、循环、`except`、`case`、`assert`、布尔运算分支和推导式条件各加 1 |
| 循环依赖 | 以文件为节点、项目内导入为边，取最大的强连通分量；分别给出全部导入、去掉 `TYPE_CHECKING` 导入、只算模块顶层导入三种结果 |
| 私有名称访问 | `obj._name` 形式的访问，且访问方文件里没有同名定义 |
| 兼容字样 | 按词边界匹配标识符和字符串，注释不计 |
| 改动热点 | `git log` 统计每个文件在回看窗口内的提交次数和增删行 |

Markdown 摘要按 ISO/IEC 25010 的可维护性子特性（模块化、可复用性、可分析性、可修改性、可测试性）分组。每个指标的完整口径和解读建议见 [`SKILL.md`](SKILL.md)。
